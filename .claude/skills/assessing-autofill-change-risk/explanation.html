assessing-autofill-change-risk

Rates one finished Autofill PR on bitwarden/clients, says how much human review it needs and which risk tag fits, with evidence for each answer, and logs whether you accepted or corrected the rating.

Workflow

1Scope the PRFetches the baseline skill, reads the PR, and widens only to imports, consumers and tests the PR touches.
↓
Checkpoint 0 - ScopeYou confirm the file list before evidence collection.
↓
2Collect evidence for every factorBaseline factors from assessing-change-risk plus six Autofill factors. Each answer is yes, no or unknown with a path and line. No level yet.
↓
Checkpoint 1 - EvidenceYou correct any answer before scoring.
↓
3Apply the rubric in a fresh subagentThe subagent sees only the evidence and the rules. Baseline level and review rules run unchanged, then Autofill rules and the external-contribution rule can only raise the requirement. It ends with a recommended tag.
↓
Checkpoint 2 - AssessmentLevel, review requirement, what raised it, and any factor that still needs a team decision. You accept the rating or correct it.
↓
4Log the outcomeAn accepted rating gets a one-line entry. A correction also records what produced the rating and whether the evidence or the rule was wrong.
↓
Checkpoint 3 - CalibrationYou confirm the entry before it's appended to references/calibration.md.

Inputs and outputs

Inputs Outputs (in your output folder)
  • PR number on bitwarden/clients (one per run)
  • Output folder outside the clients checkout
  • Optional evidence you already have, such as a community-pr-repro report
  • <pr>/baseline-skill.md
  • <pr>/scope.md
  • <pr>/evidence.md
  • <pr>/assessment.md (JSON in the marketplace skill's shape, plus Autofill fields)
  • One line in references/calibration.md per run, plus <pr>/correction.md when you correct the rating

Autofill factors

Factor Yes when the change...
vault-data-exposure sends new or more user data into the page, sends full models, sends data early, or adds a Bitwarden marker the page can see
content-script-dependencies adds a third-party package or a new import chain to a content script bundle, including a barrel reached through a narrow import
page-cost adds hot-path work, skips teardown, or alters the page DOM beyond rendering
intent-and-policy changes when autofill acts without user interaction, a default, page-signal handling, or organization policy
origin-matching changes how fills are gated on URI match
injected-ui-integrity changes how the inline menu or notification bar is positioned, shown or protected

Questions to answer at the start

The skill asks these once, writes the answers in place, and then runs as a normal skill.

SourcesShould the Autofill factors cite principles.md (still in review in PR 24688) as team policy, or label it "proposed" until it merges, and with what label text?
Escalation listWhich paths must always get an Autofill engineer's review, and which of those count as core-paths that nothing can lower?
Step 2What read-only way does the team use to see a content script bundle's module graph, if any?
Step 2Which kinds of change carry no Autofill risk on their own, such as test-only or docs-only PRs? These let a PR clear without "can't tell" answers.
Step 3Which GitHub labels does the team use for review risk, and which fits each review requirement?
Step 3For each Autofill factor, what minimum review requirement has the team agreed on? Factors without agreement are reported as needing a team decision.

How Audrey's materials shaped it

  • Evidence and rubric are separate steps. Her health reviewer observes and records, and her regulators apply a rubric without reading code. Step 2 collects evidence only, and Step 3 scores it in a fresh subagent that never sees the PR.
  • Bounded scope. Step 1 widens to imports, consumers, shared abstractions and tests, the same limit her health review uses.
  • Escalate when information is missing. Her regulators return Escalate when information is missing. Here a factor with no agreed tier goes to needs_team_decision and marks the result provisional.
  • Her investment levels are left out. Proceed, Light, Deep, Structural and Escalate size solution work before implementation. This skill rates a finished PR, so it uses the marketplace levels (low to critical) and review requirements.

Constraints

Keep in mind

  • Read-only. No checkout, build, writes to clients, or GitHub posts.
  • One PR per run. Calibrate with at least one PR the team calls higher risk and one it calls lower risk.
  • A passing repro test proves one behavior. It can support confidence for that behavior only.
  • Autofill rules only raise the review requirement. They never change a baseline answer.
  • A PR from a fork always gets at least partial review.
  • The skill recommends a tag and never applies it.
  • Deferred: CI or GitHub Action wiring, applying the tag, automatic merge, combining with the marketplace skill, and plan-time assessment.
