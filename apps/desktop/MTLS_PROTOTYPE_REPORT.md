# Linux Flatpak mTLS prototype report

Status: incomplete. Do not enable certificate management or selection from the foundation code yet.

Requirements revision: the user accepts an empty-password NSS store for the first version. Protected-store support is deferred. Client issuer/CA trust validation is not required; Authentik/the TLS terminator decides acceptance, including self-signed identities. Import must still preserve existing server trust. The revised baseline is defined in [MTLS_DETAILED_CONCEPT.md](MTLS_DETAILED_CONCEPT.md). The experiments below remain historical observations, not a claim that protected stores are impossible to support.

Those files were inspected by type and public-key match; the private key contents were not printed. A separately encrypted test `.p12` was created under the ignored `.flatpak/mtls-realtest` directory. No production app import of that identity was attempted.

The isolated probes establish that Chromium imports and selects from the app-private XDG NSS store on x86_64. They also show that Electron's direct PKCS#12 import can grant server CA trust and creates an unprotected default token. The latter is now the accepted storage baseline. Protected-store signing is deferred; controlled import without server trust changes remains required. G2 above records the old protection experiment; the detailed concept replaces that requirement with storage-boundary and passwordless-operation checks.

The endpoint normalizer, certificate selection policy, durable registry and reserved secret namespace are implemented and tested independently. They are not wired into the running app. Existing startup and network behavior remain unchanged.

## Review findings after requirements revision

- Chromium defines `-702` as generic `PKCS12_IMPORT_FAILED`; it does not identify the underlying NSS error or establish a wrong password.
- The probe returns the password file's raw UTF-8 contents. A terminal newline may be handled differently by NSS command-line password-file readers. Matching file hashes proves identical bytes, but not that those tools and the callback used identical effective password strings. This is a possible diagnostic gap, not a verified cause of the failure. A no-newline ASCII secret and recorded NSS errors would be useful if protected-store support is revisited.
- No new protected-store experiments were run for this review. The accepted passwordless version need not wait for that diagnosis.
- The helper, safe chain import, identity/key deletion, ownership reconciliation, actual main-process/IPC/UI integration, and remaining packaged tests are still missing. Accepting any client issuer does not require importing that issuer as a trusted server CA.

See [Chromium error definitions](https://github.com/chromium/chromium/blob/main/net/base/net_error_list.h) for the import error mapping.

## Direct import failure resolved

The decoder probe used `NSS_Init`, whose NSS header contract opens certificate and key databases read-only. Importing private keys requires writable initialization. Changed the probe to `NSS_InitReadWrite`.

Regression comparisons on disposable host databases using the same generated fixture:

| Initialization/case                                 | Result                                                                                              |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Original `NSS_Init`                                 | Reproduced `SEC_ERROR_PKCS12_UNABLE_TO_IMPORT_KEY` (`-8099`).                                       |
| `NSS_InitReadWrite`, empty-password token           | Import succeeded; `certutil -K` found the private key.                                              |
| Writable import with both tested CA target policies | Client had `u,u,u`; bundled CA had `,,`. CA target placement alone does not establish server trust. |
| Writable import with a previously trusted CA        | Existing `C,,` trust was preserved; client import succeeded.                                        |

Build used the already downloaded NSS/NSPR headers and host libraries:

```sh
cc -Wall -Wextra \
  -I.flatpak/nss-build-deps/sysroot/usr/include/nss3 \
  -I.flatpak/nss-build-deps/sysroot/usr/include/nspr4 \
  scripts/mtls-test-proxy/nss-import-probe.c \
  -o /tmp/bitwarden-mtls-nss-import-probe \
  -lsmime3 -lnss3 -lnssutil3 -lnspr4
```

No installed Bitwarden database or user identity was modified. This resolves the direct decoder import blocker; it does not establish packaged-browser trust isolation or a complete production helper. Next, run this controlled import in the Flatpak test environment and verify both client authentication and rejection of an otherwise untrusted server. Do not continue diagnosing the reproduced host import error as an encryption/password problem.

## Packaged helper implementation in progress

- Added `desktop_native/mtls_helper/mtls_helper.c` with a bounded one-request binary pipe protocol. It accepts PKCS#12 bytes and a UTF-8 password on stdin, returns only the public leaf certificate DER or a sanitized error, rejects multiple keyed identities, and uses `NSS_NoDB_Init` for read-only inspection and `NSS_InitReadWrite` for import. Inspection created no database in a host test. Password buffers are wiped before exit; the source-file password is never passed as an argument, environment variable, or temporary file.

A protected NSS database returned `store-password-unsupported` without resetting its password. The generated passwordless database had `0700` directories and `0600` NSS files.

## Stable identity nickname and conflict regression

- The helper now copies the public leaf certificate DER while NSS owns the decoder item. NSS reuses its iteration buffer, so retaining `item->der` after iteration produced an incorrect fingerprint. The copied DER matches the fixture's public X.509 certificate and is hashed to a lowercase SHA-256 nickname, `bw-mtls/<storeId>/<fingerprint>`. The helper requires a lowercase UUID-shaped registry `storeId` on import.
- In a disposable host NSS database, two imports of the same fixture bundle both succeeded. `certutil -L` showed one app-nicknamed client certificate and `certutil -K` showed one corresponding private key; the bundled CA remained untrusted (`,,`). This checks idempotent registration for this fixture.
- In a separate disposable database initialized with `pk12util`, the same public leaf had a non-app nickname. After setting the test database permissions to the required `0700` directories and `0600` files, the helper returned `conflict` and did not claim ownership. A first attempt returned `store-location-unsupported` because the test's `pki` directory was `0755`; that was a fixture setup error, not a conflict result.
- Reimport with the same `storeId` succeeded, while the same identity with a different `storeId` returned `conflict`; `certutil -K` still showed exactly one key. This is a host lifecycle regression, not a Flatpak removal/restart test.

## Startup selection and deletion continuation

- The desktop main process now loads a read-only registry snapshot before `WindowMain.init()` registers its Electron `ready` handler. On supported Flatpak IDs, it installs an app-level `select-client-certificate` handler that prevents Chromium's automatic first-certificate choice, checks the managed window/session, and selects only the configured offered DER fingerprint. A corrupt registry or unsafe NSS location yields an empty fail-closed snapshot while normal app startup continues. Unexpected protected-token password requests return an empty cancellation response.
- The helper gained an idempotent `delete` operation. It requires the registry `storeId` and certificate fingerprint, verifies the certificate's nickname and actual DER digest, and refuses deletion if another stored certificate references the same public key. It deletes the owned certificate and key together; bundled chain certificates are retained as untrusted material for now. A disposable host regression imported one key, left it intact for a different store ID, removed it for the matching ID, and repeated deletion with zero keys remaining.
- Queued registry cleanup is reconciled after the application's single-instance lock is held and before the first window opens. Successful deletion is followed by an atomic registry update; failures remain queued. The desktop main webpack bundle, focused unit tests, TypeScript check, ESLint, and Flatpak SDK helper compilation passed. This wiring has not yet been exercised in a packaged Bitwarden app with a real binding.
- The full Flatpak finish phase still fails in this build environment because `/usr/libexec/appstreamcli-compose` is absent. Build-only succeeds under the ignored `.flatpak` directory; the installed `com.bitwarden.desktop` Flatpak has not been updated. Management IPC, UI, complete import validation, trust snapshots, and G3/G5/G7 packaged lifecycle coverage remained open at that stage.
